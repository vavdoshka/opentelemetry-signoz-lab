Lab 4: alerts

Alerts that reach you

A dashboard only helps if someone is looking at it. This lab turns what you learned into eight alerts, and proves each one against the real failure. Six first choices turned out to be wrong, and how they were wrong is the most useful part.

Where this lab fits

This lab adds nothing to the app or to how telemetry is collected. It acts on what SigNoz already has.

Start it

Run make lab4. It needs Lab 3, because some rules read Lab 3's metrics. It does three things:

  1. Deploys a small alert sink at lab4.localhost:8080. It stands in for Slack or PagerDuty, so you can see exactly what SigNoz sends.
  2. Creates a notification channel and eight rules from labs/lab4-alerts/alerts.json.
  3. Sends a test notification and checks that it arrived. A channel that exists proves nothing.

Inside a rule

This is a whole rule, as make lab4 sends it to /api/v2/rules:

  • condition.compositeQuery is the same query you'd build in the UI.
  • thresholds says what counts as a problem, and which channel to tell. matchType decides whether one point is enough, or the whole window must match.
  • evaluation says how far back to look, and how often.
  • annotations are the words you read at 3 a.m. They can use {{$value}}, {{$threshold}} and any grouped label, such as {{$k8s.pod.name}}. {{$value}} already includes the unit, so don't add your own.

You can also build all of this in the SigNoz UI, under Alerts. Keeping rules in a file means you can review them and rebuild them. make lab4 updates rules that changed, and removes any this lab created that are no longer in the file.

So plan for about four minutes. That's a deliberate trade-off, and the time goes here:

StepTimeWhySetting
Evaluation delay2 minutesRules read data that's 2 minutes old, so late data has time to landruler.eval_delay

Grouping30 to 60 secondsAlertmanager waits to group related alerts into one messagegroup_wait, 30 seconds

Resolved notifications take longer. The window has to clear first, and then they go out on a 5-minute tick after the alert's last notification (group_interval). In this run, one fired at 19:43:51 and resolved at 19:48:51, and another went from 19:47:12 to 19:52:12.

Telemetry stopped is the slowest, because the window must be empty and absentFor then has to pass. It first used a 5-minute window, which needed about 9 minutes of silence, so the rule now uses 1 minute. These are SigNoz's defaults, and this lab doesn't change them.

What makes a good alert

  • Prove it fires. Six of this lab's first choices of signal or threshold turned out wrong, though they all sounded right. Two could never have fired. Cause the failure and watch it arrive.
  • Set the threshold above your normal. The first throttling threshold was 25%. This pod reads 19 to 32% just serving requests, so it would have flapped forever. Look at the real data first.
  • Prefer symptoms to causes. Error rate and slow queries are what users feel. Use cause-based rules, like throttling, to explain them.
  • Remember what can't report itself. A dead pod can't send an error, so watch for missing data, and read its callers.
