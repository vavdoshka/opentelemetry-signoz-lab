A failing health check

Kubernetes restarts a working app because its health check says so. This incident shows where that decision is recorded, and why the obvious chart reads zero.

1Trigger it

liveness makes /healthz return 503 from now on. Nothing else about the app changes: it still serves requests.

2Symptom

A working app restarts. Requests fail briefly, then everything looks fine again. The restart count goes up by one.

The counter trap

prober_probe_total counts probe results, so the natural chart is its rate of failures. During the first restart, that chart read 0, even though the kubelet had counted 3 failures:

Query on failed Liveness probesResult
increase or rate0
latest3
Straight from the kubelet3

A result="failed" series doesn't exist until the first failure. Its first value is already 3, and with no earlier value to compare, the increase is 0. Later failures count, but a pod's first ones don't. That's the failure you most want to see, so the dashboard shows a running total and the alert uses the event.

This isn't specific to SigNoz. Any counter that appears for the first time already above zero behaves this way.

5Root cause

Three failures, 5 seconds apart, is about 15 seconds. The kubelet doesn't know why the probe failed. It only knows the rule you gave it.

6Resolution

  • Check only what a restart can fix. Don't make liveness depend on a database or another service. If that's down, restarting this pod won't help, and every replica fails at once.
  • Use readiness for "not right now". A failed readiness probe stops traffic without killing anything.
  • Use a startup probe for slow starts, as this workload does, so liveness doesn't kill an app that's still starting.
