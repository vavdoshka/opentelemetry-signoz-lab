Lab 3: incident 2 of 5

A container that disappears

The kernel kills a container that goes over its memory limit, with no warning and no error. The metric named after this event reads 0 the whole time, so you have to know where the real evidence is.

1Trigger it

Keep some load running, then leak memory. oom allocates 2 MiB a second until the kernel steps in. That takes about 100 seconds, and only this container is affected: the limit protects the node.

2Symptom

The app reports nothing unusual, and then stops. Its last log line arrived two seconds before the kill:

There's no error and no stack trace, because the kernel gives a process no chance to write one. The app's own spans just stop. The caller tells a better story: lab3-loadgen recorded 38 failed calls, and the slowest waited 15 seconds.

4Evidence

The exit Kubernetes recorded, from kubectl get pod:

And the kernel's record of a later kill, as SigNoz received it:

It names the process, and shows it holding 254 MiB of its 256 MiB limit. The cpuset value is the container ID, and it matches exactly the one Kubernetes reported for that kill: containerd://d27ba4de75b6…. No metric tells you that much.

Exit code 137 means the process received SIGKILL. The timing fits: the app started at about 64 MiB, and (256 − 64) ÷ 2 is 96 seconds. The kill came 104 seconds after the leak started.

Why the obvious metrics miss it

  • container_oom_events_total belongs to the container's cgroup. The kill destroys that cgroup, and the replacement starts again from 0. Reading cAdvisor directly showed 0 too, so this isn't a SigNoz problem.
  • k8s.container.status.reason describes the current state. The container was running again before the next 30-second sample.

Why the limit metric misleads you both ways

k8s.container.memory_limit_utilization sounds perfect, but compare it at two moments:

MomentShare of limitWorking setRSSIn danger?
Just before this OOM kill0.863224 MiB215 MiBYes
The disk scenario, writing a file0.99561 MiB51 MiBNo
  • It read low before the kill, because it's sampled every 30 seconds and the kill came between samples.
  • It read high with no danger, because it counts page cache from the file write. The kernel can reclaim that, so nothing gets killed.

Working set leaves out that cache, so it tracks the real risk. That's why the dashboard's memory panel uses it.

5Root cause

The app keeps every block it allocates, so memory grows until it reaches the limit:

A memory limit is enforced differently from a CPU limit. Going over a CPU limit makes you wait. Going over a memory limit gets you killed, because memory can't be taken back from a running process.

6Resolution

  • Find the leak. A climbing line on Memory in use (working set) is your early warning, and you have about a minute and a half here.
  • If it isn't a leak, raise the limit to fit real usage.
  • Alert on the exit reason, not on the OOM counter. Lab 4 does this. The kernel's log line would also work for a log-based alert. Untested
