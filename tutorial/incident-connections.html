Out of connections

Postgres refuses new connections, and the next order fails. There's no failed query to look at, because the order never got as far as running one.

1Trigger it

too_many_clients opens connections and keeps them until Postgres refuses one. Then it tries to place an ordinary order, and holds the connections for 15 seconds, so the statistics catch it.

2Symptom

HTTP 503. It opened 21 connections before Postgres refused, and the next order failed too:

3What the trace shows

Very little. The request span has an error, and took 15 seconds:

What's missing is the point: there's no span for the order that failed. The agent traces queries, and that order never got far enough to run one. If you only search for failed database calls, you'll find nothing.

4What Postgres shows

Loading saved query...

Note the level, FATAL, and the code, 53300. Postgres logged each refusal, even though the app never ran a query. The statistics show how close to the limit it is, which you could alert on before anyone gets refused:

Loading saved query...

postgresql.backends peaked at 23, against a postgresql.connection.max of 30. It only counts the lab database: the app's 21, plus 2 from the collector, which has another 2 open to the postgres database.

Why monitoring gets its own connections

The limit is 30, but ordinary users only get 25: 3 are for superusers, and 2 are the reserved_connections this lab sets up for otel_monitor. We ran this incident both ways: Query API only

Monitoring's userDuring the incident
Has pg_use_reserved_connectionsEvery metric kept arriving, and postgresql.backends read 23
Doesn'tAlmost every metric kept arriving, and postgresql.backends still read 23. One, postgresql.db_size, missed one scrape, with remaining connection slots are reserved in the collector's log

The difference was small, because the collector keeps its connections open and reuses them. It would matter more if the collector had to reconnect during an incident, for example after a restart. We didn't test that. Untested

5Root cause

Each connection is a whole Postgres process, so a limit is there on purpose, and this lab sets a low one. This app keeps opening them with nothing to stop it. The collector's 4 connections count too, which is why the app got 21 of the 25.

6Resolution

Limit how many connections the app can open. Here that's a simple cap, which stands in for a connection pool, such as psycopg_pool.ConnectionPool(max_size=10) in a real app:
