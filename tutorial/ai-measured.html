Lab 5: AI analysis

How good is it?

We triggered five incidents whose causes we already knew, let real alerts start real investigations, and read every report. The results are good, with some mistakes worth seeing.

Five incidents, one run each, on one model. That's a demonstration, not a benchmark, and a different run could go differently.

How it was scored

scripts/evaluate_ai.py causes each failure for real, waits for the real alert to start an investigation, and then checks the report for the facts that Lab 3 and Lab 1 established by hand. To run it yourself, it needs Lab 5 and a login. It takes about 30 minutes and costs about $1 on Sonnet 5.5:

The text checks are simple, and they can be fooled: a report that says "not an OOM kill" contains "OOM". So we also read every report, and checked its claims against SigNoz and Kubernetes. The results are in tutorial/data/ai-evaluation.json.

What it got wrong

It said something wasn't there, when it was

In the OOM case, its report said this:

The kernel's record was in SigNoz all along, at the very moment of the kill: Memory cgroup out of memory: Killed process 3735252 (uvicorn). Its search just didn't find it, and it reported that as an absence. Those pods have no service.name, and AGENTS.md only said that the kernel log was "the output of the kernel-log pods". So we added the exact filter:

We ran the case again. It went to those pods, and found Killed process 3767198 (uvicorn) ... anon-rss:260184kB at 16:13:19, a second before the exit Kubernetes recorded. One line fixed that search. It didn't fix everything: this run missed the app's holding N MiB log lines, which the previous run had found. Runs vary, and these are one run each.

Treat "I found nothing" as the weakest thing an agent says. It means its query returned nothing, which isn't the same as nothing happening. When a report misses something, improve the runbook, as you would for a new colleague.

It didn't find what burned the CPU

It described the throttling accurately, and it said it hadn't found the cause. The answer was within reach: the app logged burning CPU with 2 processes for 300s, and there's a trace of the request that started it. It stopped once it had explained the alert.

It saw patterns in our testing

We ran these cases back to back, so it reported that memory spikes "repeat about every 25 minutes", and it read the throttling as recurring. From the data that's reasonable, and it's wrong. It can't know that someone was testing it. Our first version of the evaluation also restarted the pod before each case, and the agent duly blamed that rollout, so we stopped doing it.

And what it got right that we didn't ask for

  • It noticed that the OOM rule stays true after a single kill, so it can keep firing. That's a real weakness in our rule.
  • It separated an earlier liveness restart from a later OOM kill on the same pod.
  • It said what it hadn't checked in every report, and it was right when we were wrong.

When the evidence isn't there

An agent can only find what reached SigNoz. Our first run happened on an overloaded machine, and we found out the hard way.

What happenedWhat it did to the investigation
We left three load generators running on Docker's 4 CPUs, with other containers too, and imported an image. Docker's VM had 2% idle, and probes started timing outKubernetes killed healthy pods, including ClickHouse. Three queries timed out
One SigNoz collector got stuck, and silently dropped 19,131 log records. Gap 6 has the detailsThe liveness alert never fired for a real kill, so there was no investigation at all
The kernel log lines from one OOM kill were among those lostThe report had no kernel evidence. This time it was right that they weren't there

The agent didn't notice the stuck collector. It has no way to know what's missing. We found it because the evaluation expected an alert that never came, and we went looking. That's a reason to test your alert path with real failures, as Lab 4 does. evaluate_ai.py now records how many batches the collectors dropped during each case. In the last four results above it was 0. The slow SQL case ran first, just after the collector began failing, and everything it cited still checked out.

Every report, in full

A slow SQL query: complete

What really happened: The backend ran SELECT pg_sleep(2), so the query took 2 seconds.

Our reading: It named the SQL, the three spans and the scenario that ran them. Every number matched our own query, and it said what it hadn't checked.

API calls refused: complete

What really happened: The workload's ServiceAccount listed secrets, which its Role doesn't allow.

Our reading: It found who, what and why, from the audit log, and its count of 3,269 is exact. It didn't look for what started the calls, and says so.

A failing health check: complete

What really happened: /healthz started returning 503, so the kubelet killed the container.

Our reading: It found the request that started it, the 503s, the kill and the clean exit, and noticed that the app kept serving traffic. The event times match Kubernetes.

CPU throttling: partial

What really happened: The app burned more CPU than its 200m limit, so the kernel throttled it.

Our reading: The mechanism and the numbers are right. It didn't find what burned the CPU, and says so. It also calls our repeated test runs a recurring pattern.

An OOM kill: partial

What really happened: The app leaked memory until the kernel killed it at its 256Mi limit.

Our reading: After we added a line to its runbook, it has the best evidence: the process, its memory and the time of the kill. But it calls a steady 2 MiB a second leak a sudden spike, because it read 1-minute averages and not the app's own log. It also sees a pattern in our testing, and says it didn't find the trigger.
