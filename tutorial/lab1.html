The whole configuration

This is every piece of OpenTelemetry configuration in Lab 1. The app's code and its Kubernetes manifest don't mention OpenTelemetry at all. (Its image does contain the opentelemetry-api package, because FastAPI depends on it, but the app never imports it.)

Logs need one setting

Traces and metrics work as soon as a pod is injected. Python logs don't: the agent leaves them off by default, so without line 34 above, SigNoz would receive no application logs from it. That one setting is all it takes:

  • Everything your app writes with Python's logging goes to SigNoz.
  • Each log written during a request carries that request's trace_id and span_id, so logs link to their span.
  • Fields in extra={...} become searchable log attributes, with no OpenTelemetry code.

Other languages have their own defaults, so check yours. The node agent also collects container stdout, but those copies have no trace link. See What is missing.

What happens when a pod starts

  1. Kubernetes asks the Operator's admission webhook about each new pod.
  2. The Operator sees the annotation on the namespace, and adds an init container that copies the Python agent into the pod.
  3. It sets PYTHONPATH and the OTEL_* variables, and names the service after its Deployment, such as lab1-backend.
  4. Python loads the agent before your app, and the agent patches FastAPI, httpx, psycopg and logging.

Datadog's Single Step Instrumentation works the same way: a webhook and an init container. Injection happens at pod creation, so the Instrumentation has to exist first. Postgres opts out with inject-python: "false", because the namespace annotation applies to every pod.

The agent patches every matching library in the pod, including the load generator's HTTP client. That is why load traffic starts at a POST span in lab1-loadgen, while a click on a scenario button starts at the frontend.

The pattern is simple. Hands-off sees everything that passes through your libraries. It can't see what your code means, unless your logs already say it.

What hands-off costs

  • No custom detail on spans or metrics. You can see a slow POST /orders, but the span doesn't say which item or how much. If the app already logs those fields, you can count, sum and chart them from logs. You can't connect them to latency, and you can't see a field nobody logged.
  • No trace IDs in your app. It can't show one to a user, or put one in a support ticket, because the app doesn't know it is being traced.
  • More metrics than you asked for. The agent bundles about 50 instrumentation packages, and turns on every one that applies. That includes Python runtime, process and system metrics, so you get them with no code. It also means more metric series: in this run, one Lab 1 backend pod sent 768 metric series, and 426 of them were runtime, process and system metrics. Lab 2 runs the same agent, so it sends them too. Check the cost at scale.
  • It can fail silently. If the Operator's webhook can't answer, Kubernetes starts the pod anyway, with no agent and no error. The pod looks healthy and sends nothing. So check for the init container, which is what make up does here.
  • The platform gaps remain. Stdout logs are still duplicated, and Service Map counts stay unreliable. See What is missing.

When to use it

Start here. It costs one annotation and gives you most of what you need to debug. The next six pages prove that: each one is a real incident you can solve with this telemetry alone. When you reach something it can't answer, Lab 2 shows how to add just that detail, without re-instrumenting anything.
