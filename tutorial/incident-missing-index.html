A query that reads everything

A lookup is a little slow, and nothing else is wrong. The trace says how long it took. The plan says what it spent the time on.

1Trigger it

missing_index looks up one customer's sales by email, in a table of 500,000 rows.

2Symptom

Each lookup takes about 250 ms, to find about a dozen rows. Nothing fails. It isn't slow enough for anyone to notice one request, which is how this kind of problem grows with the table.

3What the trace shows

Loading saved query...

The span has the SQL and how long it took. Unlike the lock wait, the time really was spent working, but the span can't say on what.

4What Postgres shows

Any statement over 100 ms gets its plan logged, because of auto_explain:

Loading saved query...

Seq Scan on sales means it read the whole table. The statistics agree, because sequential scans on sales climb with each lookup:

Loading saved query...

Look at the Filter line. The settings keep values out of the log, but the plan still shows this customer's email. It's made up here. On a real system, it wouldn't be.

5Root cause

Nothing indexes lower(email), so Postgres has no choice but to read every row and compute it. An index on email alone wouldn't help: it has to match the expression in the query.
