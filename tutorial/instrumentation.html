Lab 2: custom dimensions

The instrumentation code

Lab 2 is Lab 1 plus a few lines of code. You keep the hands-off setup, and you add detail only where you need it. Nothing gets re-instrumented. This page is the whole difference between the two labs.

What stays the same

The Operator injects the same agent into Lab 2. Its labs/lab2-custom-dimensions/k8s/instrumentation.yaml matches Lab 1's, apart from the namespace and environment names. So everything from Lab 1 still arrives with no code: traces across services, SQL text, exceptions, logs, HTTP metrics and runtime metrics.

The agent sees your libraries. It can't see what your code means. So Lab 2 adds only what the agent can't know:

  • Which product an order was for, and what it cost.
  • Where the time went inside your own function.
  • Whether a lookup hit the cache.
  • Totals you want on a chart, such as revenue.
  • The trace ID, so you can give it to a user.

Each of these is a dimension: a detail you can filter or group by. Some are business details, like order.item. Others are technical, like cache.hit.

Log fields have two limits, and they are the reason Lab 2 exists:

  • You can't connect them to latency. The item is on the log, and the duration is on the span. A log has no duration, so no search can give you "P99 by item".
  • You can't see a field nobody logged. Lab 1 never logs the coupon, so it can't tell you about it. The next pages show both limits in real incidents.

The one new dependency

Lab 2 adds a single package: the OpenTelemetry API. It has no SDK and no exporters, because the injected agent provides those.

That last comment is literally true. With the agent removed from the path in a running Lab 2 pod, a new span was a NonRecordingSpan with an all-zero trace ID. Your code still runs, it just records nothing. So you can leave these calls in place anywhere the agent isn't.

Giving users a trace ID

Lab 1's app can't return a trace ID, because it doesn't know one exists. With the API, three lines fetch it, and Lab 2 adds it to every response. That is also why this tutorial's Lab 2 buttons link straight to SigNoz with no search.

This is a cheap trick worth copying: a support ticket that quotes a trace ID takes you straight to the evidence. See A customer quotes a trace ID.

Choosing where to put a dimension

Field on a logAttribute on a spanMetric
OpenTelemetry code neededNoneAPI callAPI call
Find one exampleYesYesNo
Count or sum it over timeYesYesYes
Latency by that fieldNoYesOnly if you record latency with it

Start with logs, because they cost nothing. Move a field to a span when you need to know how it affects latency. Add a metric when you want a cheap, long-lived trend or an alert.

Not covered here: a full SDK setup, with your own providers and exporters. You need that for apps outside Kubernetes, or where you can't run the Operator. This lab doesn't use one.
