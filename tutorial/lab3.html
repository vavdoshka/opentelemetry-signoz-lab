Lab 3: Kubernetes

What Kubernetes tells you

Labs 1 and 2 watch your app. This lab watches what it runs on: pods, nodes, the kubelet and the API server. Some of that comes free, but the signals that explain the worst failures don't. You'll see what they cost, and which metrics quietly mislead you.

Where this lab fits

Labs 1 and 2 cover the app. This lab covers what it runs on, and collects it through the same node agents and SigNoz.

Start it

Run make lab3. It takes a minute or two, and it does four things:

  1. Deploys a small workload in namespace lab3. Like Lab 1, it has no OpenTelemetry code.
  2. Adds four scrape jobs to the cluster collector that k8s-infra already runs.
  3. Gives that collector permission to read them.
  4. Creates five dashboards: four from SigNoz, and one for this lab.

Start some load, at the lab's page or here. Use 2 requests/s unless a page says otherwise. Stop it when you finish.

What collects it

If you've used Prometheus on Kubernetes, you might expect node-exporter, kube-state-metrics and a Prometheus server. None of those run here. k8s-infra installs OpenTelemetry collectors, and their receivers do the same jobs:

Runs asReceiverWhat it collectsDoes the job of
Node agent, one per nodekubeletstatsPod, container, node and volume usage, from the kubeletScraping usage from cAdvisor
Node agenthostmetricsThe machine: CPU, memory, disk, networknode-exporter
Node agentfilelog/k8sContainer logsA log shipper
Node agentotlpYour apps' traces, metrics and logs
Cluster collector, one in the clusterk8s_clusterObject state: restarts, node conditions, replicaskube-state-metrics
Cluster collectork8s_eventsKubernetes events, stored as logsAn event exporter
Cluster collectorprometheus/scraper, added by Lab 3Anything with a Prometheus endpointA Prometheus server

Everything then goes to SigNoz's own collector over OTLP. One rule to remember: the agents run on every node, so they collect what's local to a node. The cluster collector runs once, so it handles what would otherwise be counted twice. Its prometheus/scraper receiver is what Lab 3 adds, and it's why the kubelet and cAdvisor can be read without installing anything else.

You don't need the details to work through the incidents. How it's collected, and what it costs covers the scrape jobs and logs after them.

Logs: one copy, from stdout

In Labs 1 and 2, every app log reaches SigNoz twice. The agent in the app sends it over OTLP, and the node agent's filelog/k8s receiver reads the same line from the container's output. Lab 3's app sends its logs one way only: it prints them, and the node agents collect them along with every other container's output, with nothing set up per app. Three settings in its Instrumentation do it:

ToSettingWhy
Avoid the second copyOTEL_PYTHON_LOG_AUTO_INSTRUMENTATION=falseThe app stops sending logs over OTLP. They still reach SigNoz, from stdout
Keep the trace linkOTEL_PYTHON_LOG_CORRELATION=trueThe agent writes the trace and span IDs into each line. The node agent can't find them any other way: they only exist inside the app's process
Know what to parseOTEL_PYTHON_LOG_FORMATThe exact line format. The pipeline below expects it, so change the two together

The IDs are now text, and SigNoz links a log to a trace only through the log's own trace fields. So make lab3 also creates a SigNoz log pipeline from labs/lab3-kubernetes/log-pipeline.json. It runs in SigNoz's own collector, and you can see it in SigNoz under Logs, then Pipelines. It matches the line format, not a namespace, so it parses any app that prints it. What it costs, measured on Lab 1

The same 3 warnings and one crash, before and after applying these settings to Lab 1, as in the steps below:

OTLP and stdout (Lab 1 as shipped)Stdout only
3 warnings6 records: 3 linked, 3 with no link, level or service3 records, all linked, with level and service
The crash's log line2 records. The OTLP one holds the whole stack trace1 record, linked
The traceback124 records, one per line, unlinked123 records, one per line, unlinked
extra= fieldsOn the OTLP copyLost
  • extra= fields are lost. The line carries only the message, so a search or chart on a field, like Lab 1's order.total, finds nothing. Keeping fields needs OTLP, or JSON logs that a pipeline can parse.
  • A traceback becomes one record per line, with no link. The exception isn't lost: the request's span still carries it as an exception event, about 3,100 characters here.
  • The app's own log format is replaced. The agent sets up logging before the app does, so Lab 1's logging.basicConfig(format=...) did nothing. An app that forces its own setup, with force=True or dictConfig, would print no IDs. Put %(otelTraceID)s and %(otelSpanID)s in its own format instead.
  • uvicorn's own lines never carry IDs: its access log and tracebacks use its own format.

What you gain is one copy of each line, the same as kubectl logs shows, and one collection path for every container, including those with no agent. Lab 4's alert on Lab 1's error logs still matches after the change, because the pipeline sets the level it filters on.
