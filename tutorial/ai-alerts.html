1Give it a login

The investigator runs Claude Code inside the cluster, so it needs its own login, which make lab5 can't create for you. On a paid Claude plan, run this in your own terminal. It prints a token valid for a year, meant for scripts and CI:

Save it from the repo's root. This reads it without showing it. The file is git-ignored, and only you can read it:

That's for zsh. In bash, replace the read with read -rsp 'Paste the token: ' TOKEN. With an API key instead, the line in the file is ANTHROPIC_API_KEY=..., and it's billed per token. Then run make lab5 again. It puts the file into a Secret, and its smoke test makes Claude Code answer one word from inside the pod.

This is ordinary alert routing. make lab5 adds a webhook channel next to Lab 4's, on the rules listed in labs/lab5-ai/investigate.json. Not every alert should start a paid investigation. 4What it found

This is its whole report, unedited, from a run triggered at 14:12:29:

StepTime
From the failure to the alert reaching the investigator301 s. That's SigNoz's alert delay, covered in Lab 4
The investigation116 s, in 9 turns
Cost$0.24, on Sonnet 5.5

So the cause was waiting for whoever got paged about 7 minutes after the failure. We checked its claims by querying SigNoz ourselves:

What it saidWhat SigNoz shows
Three SELECT pg_sleep spans, of 2.033, 2.033 and 2.010 secondsThe same three spans, and the same durations
Their trace IDs, and the pod lab1-backend-5fdf895ff4-zqw8xThe same
Two INSERT INTO orders spans, of 906 and 558 ms, at 14:14, too short to fire the alertThe same two

It separated the failure from the noise. Normal traffic was running, including requests that are slow on purpose. It noticed that those INSERT spans were under the threshold, and said so. It also said what it hadn't checked: Postgres itself, the node, and who triggered the scenario.

5What keeps it under control

LimitWhy
MAX_BUDGET_USD, $1.00Stops one investigation at Claude Code's own cost estimate. It can overshoot a little
MAX_PER_HOUR, 10A flapping alert can't run up a bill. Past that, an alert gets a note saying it wasn't investigated
MAX_TURNS, 40Stops a loop that isn't getting anywhere
One at a timeIf many alerts fire together, they wait in a queue. It keeps cost predictable, at the price of a later answer
One investigation per alertAlertmanager repeats notifications. The alert name and start time identify a firing, so repeats are ignored

The reports are kept in the pod, so replacing the pod loses them. In production you'd post them to the incident channel, which is the part this lab doesn't build.

It doesn't fix anything. It can't: both of its logins are read-only. Letting an agent act on production is a much bigger decision than letting it read, and this lab doesn't need it to show the value.
