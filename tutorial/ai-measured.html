Lab 6: AI analysis

How good is it?

We triggered five incidents whose causes we already knew, let real alerts start real investigations, and read every report. Most of it was right, one was confidently wrong, and the difference is worth seeing.

Five incidents, one run each, on one model. That's a demonstration, not a benchmark, and a different run could go differently.

How it was scored

scripts/evaluate_ai.py causes each failure for real, waits for the real alert, runs the agent on your machine on it, and checks the report for the facts that Lab 3 and Lab 1 established by hand. It needs Labs 1 to 5 and Claude Code. It takes about 30 minutes and costs about $1 on Sonnet 5.5, on your plan or API key:

The text checks are simple, and they can be fooled: a report that says "not an OOM kill" contains "OOM". So we also read every report, and checked its claims against SigNoz and Kubernetes. The results are in tutorial/data/ai-evaluation.json.

We didn't time a person doing this, so we can't tell you it's faster than you. What we can say: whoever gets paged finds a report with evidence and sources already waiting, for about 20 cents.

What it got wrong

It blamed the wrong thing, plausibly

In the health check case, it saw the kill and the 503s, and it blamed CPU throttling. That reads well, and it gave its confidence as medium. But a process that's too slow times out. It doesn't answer 503. The real cause was in the app's own log, at the moment it started:

The throttling it saw was real, too. It came from the test case before this one.

An earlier run of this same case got it completely right. It read kubectl logs --previous, found the request that started it, and noticed that the app kept serving traffic. Same model, same instructions, same failure, and a different answer. One run tells you little, and a confident report can still be wrong, so check its evidence before acting on it.

It said something wasn't there, when it was

In an earlier OOM run, its report said this:

The kernel's record was in SigNoz all along, at the very moment of the kill: Memory cgroup out of memory: Killed process 3735252 (uvicorn). Its search just didn't find it, and it reported that as an absence. Those pods have no service.name, and AGENTS.md only said that the kernel log was "the output of the kernel-log pods". So we added the exact filter:

Since then, it goes to those pods. In the OOM run above, it found Killed process 3929106 (uvicorn) ... anon-rss:259956kB at 17:53:19, the same second as the exit Kubernetes recorded. One line fixed that search.

Treat "I found nothing" as the weakest thing an agent says. It means its query returned nothing, which isn't the same as nothing happening. When a report misses something, improve the runbook, as you would for a new colleague.

It stopped once it had explained the alert

In the throttling and OOM cases, it described what happened accurately, and it said it hadn't found what started it. The answer was within reach both times: the app logged what it was doing, and there's a trace of the request that started it. It's worth asking the follow-up: "now find what started it".

It saw patterns in our testing

We ran these cases back to back, so in earlier runs it reported that memory spikes "repeat about every 25 minutes", and it read the throttling as recurring. From the data that's reasonable, and it's wrong. It can't know that someone was testing it. Our first version of the evaluation also restarted the pod before each case, and the agent duly blamed that rollout, so we stopped doing it.

And what it got right that we didn't ask for

  • It matched the audit log's count of refused calls to the app's own log: exactly 1,809 in both.
  • In an earlier run, it noticed that the OOM rule stays true after a single kill, so it can keep firing. That's a real weakness in our rule.
  • It said what it hadn't checked in every report, and once it was right when we were wrong.

When the evidence isn't there

An agent can only find what reached SigNoz. An early run happened on an overloaded machine, and we found out the hard way.

What happenedWhat it did to the investigation
We left three load generators running on Docker's 4 CPUs, with other containers too, and imported an image. Docker's VM had 2% idle, and probes started timing outKubernetes killed healthy pods, including ClickHouse. Three queries timed out
One SigNoz collector got stuck, and silently dropped 19,131 log records. Gap 6 has the detailsThe liveness alert never fired for a real kill, so there was no investigation at all
The kernel log lines from one OOM kill were among those lostThe report had no kernel evidence. This time it was right that they weren't there

The agent didn't notice the stuck collector. It has no way to know what's missing. We found it because the evaluation expected an alert that never came, and we went looking. That's a reason to test your alert path with real failures, as Lab 4 does. evaluate_ai.py now records how many batches the collectors dropped during each case. In all five results above it was 0.

Every report, in full

A slow SQL query: complete

What really happened: The backend ran SELECT pg_sleep(2), so the query took 2 seconds.

Our reading: It named the SQL, all six spans and the request that started them, and said what it hadn't checked. Every number matched our own query.

API calls refused: complete

What really happened: The workload's ServiceAccount listed secrets, which its Role doesn't allow.

Our reading: It found who, what and why, and cross-checked three sources: the alert, the audit log and the app's own log, which agree on exactly 1,809. It didn't look for what started the calls, and says so.

A failing health check: wrong cause

What really happened: /healthz started returning 503, so the kubelet killed the container.

Our reading: It found the kill, and the 503s. Then it blamed CPU throttling, with medium confidence, and said it hadn't confirmed that. The real cause is the scenario request that made /healthz return 503, which is in the app's log and in a trace it didn't read. The throttling it saw came from the previous test case.

CPU throttling: partial

What really happened: The app burned more CPU than its 200m limit, so the kernel throttled it.

Our reading: The mechanism and the numbers are right. It didn't find what burned the CPU, and says so: it didn't read traces.

An OOM kill: partial

What really happened: The app leaked memory until the kernel killed it at its 256Mi limit.

Our reading: It has the best evidence: the process, its memory and the time of the kill, from the kernel log. But it calls a steady 2 MiB a second leak a sudden allocation, because it read 1-minute samples and not the app's own log, and it says it didn't find the cause of the ramp.
