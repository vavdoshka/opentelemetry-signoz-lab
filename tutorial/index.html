Hands-on tutorial

Learn telemetry by breaking a real app

This tutorial teaches you what OpenTelemetry can do for an app with no code at all, how to add detail only where you need it, how to watch the Kubernetes underneath, how to get alerted, and how to let an AI agent investigate. You work on small Python apps that fail on demand.

What you're working with

Everything runs on your machine, in one Kubernetes cluster. The number on each part is the lab that adds it. Each lab's first page shows this diagram again, with that lab's parts highlighted.

In words, from the top:

  1. The apps. Your browser calls frontend, which calls backend, which uses Postgres. It's a small shop that fails on demand. Lab 3 adds lab3-workload, which fails in ways only Kubernetes can show.
  2. Getting telemetry out. The OpenTelemetry Operator adds a Python agent to each app pod as it starts. The agent sends traces, logs and metrics over OTLP to a node agent.
  3. Collecting the rest. Node agents also read every container's output, and collect pod and node metrics. Lab 3 adds more from the kubelet, the kernel and the API server.
  4. Storing and reading it. Two SigNoz collectors write everything to ClickHouse, and the SigNoz UI and API read it from there.
  5. Acting on it. Lab 4's alert rules post to a small alert sink. Lab 6's AI agent runs on your machine, and reads through an MCP server and a read-only Kubernetes account.

Is Postgres auto-instrumented? No. The agent only works inside Python processes, so nothing runs inside Postgres, and its pod opts out. SigNoz still learns about it from three places outside it API:

  • Its queries, from the backend. The agent in backend wraps its database driver, and records one client span per query, with the SQL in db.statement and how long the backend waited.
  • Its log lines, from the node agents. They read what Postgres prints. Those lines have no service.name, so search with k8s.container.name = 'postgres'.
  • Its pod's CPU and memory, from the kubelet.

SigNoz is at signoz.localhost:8080. There's nothing to sign up for: make up created an admin account and saved its login in .lab-credentials, in the repo's root. Git ignores that file, and only your user can read it. To see the login:

Then, on SigNoz's login page:

  1. Enter the SIGNOZ_EMAIL value, which is admin@lab.local, and choose Next.
  2. Enter the SIGNOZ_PASSWORD value, which was generated for your lab, and choose Sign in with Password.

Stay logged in, in the browser you're reading this in. This tutorial's links into SigNoz open in new tabs and use that login. If you aren't logged in, they stop at the login page, and carry on to where they were going once you sign in. The live buttons and searches on these pages don't need it, because the tutorial's server reads the same file.

The file is only missing if someone created the admin by hand on SigNoz's sign-up page before make up could. Use that login instead, and save it in the file as the README's troubleshooting section shows.

When you change code

Some pages suggest a fix or a change. Saving a file changes nothing by itself, because the pods keep running the image from the last build. To try a change:

  1. Edit the file, and save it.
  2. Deploy it with that lab's make command, from the repo's root.
  3. Check it. Fire the same scenario again, and look in the same place in SigNoz.
  4. Put the bug back, because other pages need it: run git restore on the file, then the same make command again.
What you changedRun
labs/lab1-hands-off/make lab1
labs/lab2-custom-dimensions/make lab2
labs/lab3-kubernetes/make lab3
labs/lab4-alerts/make lab4
signoz/make up
cluster/make down, then make up. These settings only apply when a cluster is created, and this deletes all its data

The same commands work on k3d and kind. For example, make lab1 does this:

  1. Builds the image from labs/lab1-hands-off/app, with docker build.
  2. Loads it into the cluster, because nothing here is pulled from a registry.
  3. Applies the lab's manifests in k8s/, so changes to its YAML take effect too.
  4. Restarts the lab's pods. The image's tag, telemetry-lab1:dev, never changes, so Kubernetes wouldn't notice a new build otherwise.
  5. Checks that every pod that should have an agent got one.
  6. Runs the smoke test, which sends orders until traces, logs and metrics reach SigNoz.

make lab1 and make lab2 took 45 to 101 seconds here, and make lab3 about 3 minutes. They restart the load generator too, so any traffic you started stops, and you need to start it again. Postgres doesn't restart, so your test orders stay. Once, while we rebuilt several times in a row, docker build failed with failed to prepare extraction snapshot. Running the same command again worked.

Your path

Go in order if this is new to you, using the sidebar or the links at the bottom of each page. Each incident stands alone, so you can also jump straight to one. Mark a page complete at the bottom of it. Your progress stays in this browser.

What you will be able to do

  • Explain traces, metrics and logs, and how they connect.
  • Get traces, logs and metrics from an app without touching its code.
  • Work through six incidents using that telemetry alone, from symptom to root cause to fix.
  • Add a dimension where you need one: first a field on a log line, then an attribute on a span, then a metric.
  • Work through four incidents that show what those dimensions buy you.
  • Debug throttling, OOM kills, failed probes, and node and API server problems.
  • Write alerts on metrics, traces and logs, and prove that they reach you.
  • Connect an AI agent with read-only access, and judge how far to trust its reports.
  • Write SigNoz searches for traces, logs and metrics.
  • Spot what a plain install leaves out, including the places where SigNoz can mislead you.

About the saved examples

  • Saved trace IDs, numbers and screenshots come from real runs on 2026-11-07 and 2026-11-08.   • Screenshots show UTC+1, so 11:00 UTC appears as 12:00. Saved trace IDs exist only in the lab that made them, so their SigNoz links will not open in yours. Use the live buttons to create your own.
  • SigNoz keeps traces and logs for 15 days, so saved trace links stop working after about 2026-11-22. The pages still show the saved copy.
  • The scenarios fail on purpose, so each root cause is a known line of code. The method is what carries over to real incidents.
