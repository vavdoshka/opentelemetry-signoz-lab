Lab 3: Kubernetes

What Kubernetes tells you

Labs 1 and 2 watch your app. This lab watches what it runs on: pods, nodes, the kubelet and the API server. Some of that comes free, but the signals that explain the worst failures don't. You'll see what they cost, and which metrics quietly mislead you.

Start it

Run make lab3. It takes a minute or two, and it does four things:

  1. Deploys a small workload in namespace lab3. Like Lab 1, it has no OpenTelemetry code.
  2. Adds four scrape jobs to the cluster collector that k8s-infra already runs.
  3. Gives that collector permission to read them.
  4. Creates five dashboards: four from SigNoz, and one for this lab.

Start some load, at the lab's page or here. Use 2 requests/s unless a page says otherwise. Stop it when you finish.

A workload with real limits

What collects it

If you've used Prometheus on Kubernetes, you might expect node-exporter, kube-state-metrics and a Prometheus server. None of those run here. k8s-infra installs OpenTelemetry collectors, and their receivers do the same jobs:

Runs asReceiverWhat it collectsDoes the job of
Node agent, one per nodekubeletstatsPod, container, node and volume usage, from the kubeletScraping usage from cAdvisor
Node agenthostmetricsThe machine: CPU, memory, disk, networknode-exporter
Node agentfilelog/k8sContainer logsA log shipper
Node agentotlpYour apps' traces, metrics and logs

Cluster collectork8s_eventsKubernetes events, stored as logsAn event exporter

Everything then goes to SigNoz's own collector over OTLP. One rule to remember: the agents run on every node, so they collect what's local to a node. The cluster collector runs once, so it handles what would otherwise be counted twice. Its prometheus/scraper receiver is what Lab 3 adds, and it's why the kubelet and cAdvisor can be read without installing anything else.

On k3s, it's all one process

k3s runs the API server, scheduler, controller manager and kubelet in one process, sharing one set of metrics. You can see that in what each endpoint returns:

EndpointSeriesMetric names
API server /metrics32,461454
Kubelet /metrics on the server node32,429454
Kubelet /metrics on the worker node1,797227

The first two are nearly the same data. That makes the keep-list more important here, because a plain scrape of both would store everything twice. It also means the API server's endpoint gives you the scheduler's metrics on k3s, which you wouldn't get on a real cluster.

You can see this on the dashboards. Go Routines reads about 11,600, double the real 5,600 or so, because the kubelet and apiserver jobs both report the same process.

The kernel log

The collector can't read the kernel log itself, so a small DaemonSet does it. Each pod reads its node's /dev/kmsg and prints what it reads, and the node agent collects that like any other pod log:

It's the best evidence of an OOM kill, as that incident shows. Two costs come with it. Reading /dev/kmsg needs a privileged container, which is a real trade-off on a shared cluster. And on k3d both nodes share one kernel, so every line arrives twice, once from each pod.

The audit log

The API server's metrics show that something is busy, not who. The audit log records who made each request. Kubernetes writes none of it unless the API server starts with a policy, so the cluster config passes one:

On kind it's the same four settings, as a kubeadm patch in cluster/kind-config.yaml, plus mounts for the policy and the log, because there the API server runs as a pod.

The policy, in cluster/audit-policy.yaml, decides what's worth writing. The API server checks each request against its rules in order, and the first match wins:

RequestsLevelWhy
Requests that aren't for an object: API discovery, health checks, metricsNone58% of all requests at idle, mostly controllers and kubectl asking which APIs exist
Leases and eventsNoneEvery node and controller renews a lease every few seconds, and Lab 3 already collects events
Token and permission checksNoneThe API server checking on another component's behalf
Reads by the cluster's own componentsNoneThe API server, controllers, scheduler, kubelets and kube-system service accounts read constantly
Everything elseMetadataEvery request from apps and people, and every change by anyone

Metadata records the caller, verb, object and response code, but never the request or response body, so secrets' contents stay out of the log. Logging everything at that level wrote 219 events a minute on this idle cluster, about 290 MB a day. This policy writes about 12 a minute, or 14 KiB.

A rule that names users and groups needs both to match. The first version of this policy put the system users and the system groups in one rule, expecting either to match. Kubernetes requires both, so the rule matched nothing and those reads stayed in the log. Measure the log after changing the policy.

The API server reads the policy when it starts. To apply a change on k3d, run k3d cluster stop signoz-lab, then make up. Don't restart just the server node: it comes back with a new IP, and k3d's load balancer and the other node keep using the old one.

Why it needs its own reader

The API server writes the file so only root can read it: mode 0600, in a 0700 directory. The node agents run as user 10001, so they get permission denied. Running the agents as root would fix that, but they also mount the node's whole filesystem, so they could then read every root-only file on it, including the kubelet's keys. Instead, a small DaemonSet in labs/lab3-kubernetes/k8s/audit-log.yaml runs as root with only the audit directory mounted, read-only, and prints each new line:

Its output is a pod log. The chart's own pod log receiver skips it, and the filelog/audit receiver reads it instead. That receiver keeps the whole event as the body, and copies the fields worth searching on into attributes:

AttributeWhat it holds
k8s.audit.userWho: a user, or system:serviceaccount:<namespace>:<name>
k8s.audit.user_agentThe client program, such as python-httpx/0.28.1
k8s.audit.verbget, list, watch, create, update, patch, delete
k8s.audit.resource, k8s.audit.namespaceWhat they asked for
k8s.audit.uriThe full path
k8s.audit.codeThe answer: 200, 403 and so on

The API server incident uses it to find who flooded the API server, and the refused requests its metrics never counted.

The kubelet on kind

On kind, as on most kubeadm clusters, the kubelet and containerd run under systemd and log to journald. kind keeps the journal in memory, in /run/log/journal. Its files are readable by group 0, which the node agents run in, but they're in journald's binary format. The collector's journald receiver reads them by running journalctl, and the agents' image doesn't have it. So another small DaemonSet runs journalctl and prints each entry as JSON:

These lines reach SigNoz on kind 0.22 locally and kind 0.33 in CI. Both services are quiet at idle, with no lines in a minute. Starting this reader and restarting CoreDNS made them write 84 lines across the two nodes. During an OOM kill, containerd logged TaskOOM with the container's ID, and the kubelet only logged removing the container. The OOM incident shows both.

The node logs cost little next to the metrics: at idle, about 12 audit events and a few k3s lines a minute, roughly 15 KiB. The scrape jobs add about 6,000 series. The sample count also includes Lab 3's own two instrumented pods, and the memory figures include those pods and Lab 4's sink. We can't say how much of ClickHouse's rise is new data and how much is caching from opening dashboards.

Each job started with a shorter keep-list, which left some community dashboard panels empty. Filling them all added 17% more samples, and made no measurable difference to ClickHouse's CPU or memory at this size. So the lab keeps them. On a big cluster these series multiply, so measure before you copy this.

  • Collector memory rises whatever you keep, because it has to read about 73,000 lines every 30 seconds before throwing most of them away.
  • The API latency histogram is the biggest single item. It's about 4,250 series, for one panel. It stays because P99 latency is the main measure of API server health. If you don't need it, remove apiserver_request_sli_duration_seconds_(bucket|sum|count) from the keep-list.
  • A switch you might not expect. Turning on presets.prometheus also starts a job that scrapes SigNoz's own ClickHouse, ZooKeeper and collectors. That added 5,239 series, so this lab limits it to namespace lab3, which turns it off.
