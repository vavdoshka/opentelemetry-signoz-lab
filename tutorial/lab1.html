Logs: one setting, and the name to use

Traces and metrics work as soon as a pod is injected. Python logs are sent by the agent's logging instrumentation, and line 37 above sets it explicitly:

In this version of the agent it's already on by default, so the line changes nothing. It's there so you can see the setting, and so Lab 3 can turn it off. You don't set it on your app: everything under python.env in the Instrumentation is added to each injected pod by the Operator, so your code and your Deployment stay as they are. With it:

  • Everything your app writes with Python's logging goes to SigNoz over OTLP.
  • Each log written during a request carries that request's trace_id and span_id, so logs link to their span.
  • Fields in extra={...} become searchable log attributes, with no OpenTelemetry code.

Older guides use another name. OTEL_PYTHON_LOGGING_AUTO_INSTRUMENTATION_ENABLED=true is deprecated in the agent this lab runs (0.66b1). It still works, but setting it to false doesn't stop logs: the logging instrumentation then sends them with its own handler. Only OTEL_PYTHON_LOG_AUTO_INSTRUMENTATION=false stops them. Tested in the lab1 pod

Each of these logs is stored twice. The app also prints every line to stdout, and the SigNoz agent on each node reads every container's output. That second copy has no trace link, no level and no service name. Lab 3 shows how to keep one copy and still link it to its trace: see Logs: one copy, from stdout. Other languages have their own defaults, so check yours.

The other variables are nice to have

The rest of python.env isn't needed for telemetry to work. Each one tidies something up:

What happens when a pod starts

  1. Kubernetes asks the Operator's admission webhook about each new pod.
  2. The Operator sees the annotation on the namespace, and adds an init container that copies the Python agent into the pod.
  3. It sets PYTHONPATH and the OTEL_* variables, and names the service after its Deployment, such as lab1-backend.
  4. Python loads the agent before your app, and the agent patches FastAPI, httpx, psycopg and logging.

Injection happens at pod creation, so the Instrumentation has to exist first, and pods that are already running need a restart.

Which pods get the agent

Line 11 above opts in the whole namespace: inject-python: "true" on the lab1 Namespace covers every pod created in it, so no Deployment has to change. A pod can opt out by setting the same annotation to "false" on itself, which overrides the Namespace. Two pods here do:

PodAgent?Why
lab1-frontend, lab1-backendYesThey're the app
postgresNoIt isn't a Python app, so a Python agent has nothing to patch. You still see its queries, as database spans from the backend
lab1-loadgenNoIt only makes traffic. Traced, it would add spans that aren't the app, and each trace would start in a different place depending on whether load or a person sent it
