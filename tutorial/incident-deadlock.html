An order that gets cancelled

Two orders arrive together, and Postgres cancels one. This time the trace does say what happened. Postgres adds which statements were involved, and how often it happens.

1Trigger it

deadlock places two orders at once. Each one needs the same two rows, and they take them in opposite orders.

2Symptom

HTTP 500 after about 1.5 seconds: {"error": "DeadlockDetected", "failed_orders": 1}. One order failed, and the other succeeded.

3What the trace shows

This time the trace knows quite a lot. The failed UPDATE took 1,055 ms, and its exception event says what happened:

About a second is no accident: that's deadlock_timeout, which is how long Postgres waits before it checks for a deadlock. The exception tells you it was a deadlock, and which processes were involved. Look at its last line, though: for the queries, it sends you to the server log.

5Root cause

The first order holds coffee and wants bagel. The second holds bagel and wants coffee. Neither can ever finish, so Postgres cancels one. The barrier only makes the timing certain here. In real traffic it happens now and then, under load, which is what makes it hard to reproduce.

6Resolution

Always take rows in the same order. Then the second order just waits for the first:

Retrying also works, because Postgres has already rolled the cancelled transaction back. Code 40P01 tells you it's safe.
