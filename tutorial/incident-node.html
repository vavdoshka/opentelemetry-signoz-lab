Is it the pod or the node?

Before you debug a pod, find out whether the fault is really the pod's. Node and kubelet metrics answer that, with some limits worth knowing.

  • 1. Trigger it
  • 2. Symptom
  • 3. Where to look
  • 4. Evidence
  • 5. Root cause
  • 6. Resolution

1Trigger it

disk writes 512 MiB to an emptyDir volume, which lives on the node's disk. It removes the file two minutes later. It doesn't try to fill the disk, because that would make a real node, or your laptop, unhappy.

2Symptom

When an app misbehaves, one of your first questions is whether the fault is the pod's or the node's. A pod can be slow because of its own code, or because something else on the node is using the disk, memory or CPU.

3Where to look

Open the Kubernetes Node Metrics - Detailed dashboard, and then Kubernetes Kubelet. For a quick view, Infra Monitoring's Hosts tab shows the same nodes.

4Evidence

Disk used on each node, from k8s.node.filesystem.usage:

BeforeFile heldAfter removal
k3d-signoz-lab-server-0, which ran the pod98,912 MiB99,379 MiB98,886 MiB
k3d-signoz-lab-agent-0, which didn't98,910 MiB99,369 MiB98,873 MiB

Three things stand out:

  • Both nodes rose by the same amount, although only one wrote the file. k3d nodes are containers on one Docker VM, so they share a disk. On real nodes, only the pod's node would change.
  • The pod's own metric didn't move. k8s.pod.filesystem.usage stayed at about 32.7 MB, because it doesn't include emptyDir volumes. k8s.volume.available for that volume reports the whole disk. So you can see a node's disk filling up, but not which pod's emptyDir did it.
  • The write looked like a memory problem. k8s.container.memory_limit_utilization jumped to 0.995, while working set stayed at 61 MiB. That's page cache, and it's harmless. The OOM incident explains why it matters.

5Root cause

Here the cause is simply the scenario. The useful part is the reasoning you can reuse:

What you seeLikely fault
One pod is struggling, and its node looks fineThe pod: its limits, its code, or its dependencies
Several pods on one node are strugglingThe node, or a noisy neighbour on it
Pods on every node are strugglingSomething shared: a dependency, the network or the control plane

6Resolution

  • Set a sizeLimit on emptyDir, as this workload does. The kubelet evicts a pod that goes over it, so one pod can't fill a node.
  • Watch for trends. A disk that rises slowly is easy to miss, and an alert on available space is cheap.
  • Be careful with k3d's node numbers. Both nodes share one VM, so don't read differences between them as real.
